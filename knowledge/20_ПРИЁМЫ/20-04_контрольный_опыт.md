# Контрольный опыт

## Правило

**Ни один вывод не считается сделанным, пока не показан контрольный опыт.**

«Не пингуется» само по себе не значит ничего. Это может быть:

* защита работает;
* цели не существует;
* цель есть, но не отвечает своим фаерволом;
* трафик ушёл не туда.

Различить их можно только парой измерений.

## Три формы контрольного опыта

### 1. Снять защиту на несколько секунд

```
/interface bridge port set [find bridge=guest-bridge] horizon=none
... проверка ...
/interface bridge port set [find bridge=guest-bridge] horizon=1
```

С защитой — ARP не разрешается, ping 0 из 6. Без защиты — ARP разрешился,
ping 4 из 4. Теперь ясно, что блокирует именно horizon, а не молчаливая цель.

Так делать можно, когда окно короткое, а устройства свои. На общей сети —
только с согласия человека.

### 2. Та же цель из другой сети

Проверять **одни и те же адреса** из изолированной и из доверенной сети:

| Цель | Из гостевой | Из локальной |
|---|---|---|
| роутер, порт SSH | закрыто | **открыто** |
| хост за туннелем | нет ответа | **отвечает** |

Правая колонка обязательна. Без неё нельзя отличить «заблокировано» от
«там ничего нет».

### 3. Счётчик со стороны роутера

Если на правиле `drop` выросли цифры — блокировка доказана без всякой
контрольной сети. Если все `drop` по нулям, а трафик был — значит
**разрешено** ([10-03](../10_API/10-03_счётчики_правил.md)).

## Побочная польза от испорченного измерения

Иногда сорванный опыт даёт доказательство сильнее задуманного.

После снятия horizon MAC соседа остался в ARP-кэше Windows (`arp -d` без
прав администратора не работает, [30-07](../30_ГРАБЛИ/30-07_arp_d_без_админа.md)).
Значит кадры адресовались **прямо ему**, в обход ARP, — и всё равно не
проходили. Это доказывает, что режется сам путь данных, а не только
обнаружение соседа. Задуманный опыт показал бы меньше.

## Чем подтверждено

Пара измерений horizon=1 / horizon=none на двух устройствах в одной
гостевой сети; повторно — на устройствах в разных диапазонах.
