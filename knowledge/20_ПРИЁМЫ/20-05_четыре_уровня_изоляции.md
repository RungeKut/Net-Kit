# Четыре уровня изоляции гостевой сети

## Зачем разделять

Каждый уровень закрывает то, что не может закрыть другой. Пропустишь
один — дыра останется, а остальные три создадут ощущение защищённости.

| Уровень | Механизм | Что закрывает | Где работает |
|---|---|---|---|
| 1 | `default-forwarding=no` на точке | гость ↔ гость на одном SSID | канальный, до IP |
| 2 | `horizon=N` одинаковый на портах моста | гость ↔ гость на разных SSID | канальный, в мосту |
| 3 | правило forward на список внутренних сетей | гость → любые внутренние сети | IP |
| 4 | правило input на интерфейс гостя | гость → сервисы роутера | IP |

**Уровни 1 и 2 фаерволом не заменяются.** Трафик между клиентами одного
моста коммутируется на канальном уровне и в цепочки фильтра не попадает
вовсе — счётчики это подтверждают: при попытке достучаться до соседа
не вырос ни один.

## Уровень 1 и 2: почему нужны оба

`default-forwarding=no` действует **только внутри одной точки доступа**.
Гости на 2,4 ГГц и на 5 ГГц сидят на разных интерфейсах, но в одном
мосту — и мост пересылал бы кадры между ними.

Закрывает `horizon`: порты с **одинаковым** значением не пересылают друг
другу. На трафик к самому мосту (то есть к роутеру, за DHCP и шлюзом)
horizon не влияет — интернет у гостей работает.

```
/interface bridge port set [find bridge=guest-bridge] horizon=1
```

## Уровень 3: список вместо перечисления сетей

Не перечислять внутренние сети по одной — завести список и запретить
его целиком. Тогда новая внутренняя сеть закрывается сама.

```
/ip firewall address-list add list=INTERNAL address=10.0.0.0/8
/ip firewall address-list add list=INTERNAL address=172.16.0.0/12
/ip firewall address-list add list=INTERNAL address=192.168.0.0/16
/ip firewall address-list add list=INTERNAL address=169.254.0.0/16
/ip firewall address-list add list=INTERNAL address=100.64.0.0/10
```

Правила, в порядке:

```
chain=forward in-interface=<гость> dst-address-list=INTERNAL  action=drop
chain=forward in-interface=<гость> out-interface-list=WAN     action=accept
chain=forward in-interface=<гость>                            action=drop
chain=forward out-interface=<гость>                           action=drop
```

**Ставить после `accept established,related`**, иначе обратный трафик из
интернета не пройдёт и у гостей пропадёт связь.

Четвёртое правило — «внутрь к гостям нельзя». Нужно не всегда: входящее
направление обычно доверенное, и именно оно ломает управление IoT-
устройствами. Решать осознанно.

## Уровень 4: закрыть роутер, не сломав DHCP

```
chain=input in-interface=<гость> protocol=udp dst-port=67 action=accept
chain=input in-interface=<гость>                          action=drop
```

**Разрешение DHCP обязательно** — проверено: без него гости не получают
адрес, счётчик на разрешающем правиле растёт при каждом подключении.

Позиция: перед **первым** разрешающим правилом, которое может поймать
трафик гостя. Обычно это `accept ICMP`, но если выше стоят разрешения
VPN-портов — то перед ними, иначе порты роутера останутся открыты.

DNS гостям давать **внешний** (`8.8.8.8`), а не роутер. Тогда роутер им
не нужен вообще и закрывается целиком.

## Чем проверять

Полный список проверок — [20-04](20-04_контрольный_опыт.md) и
`netkit/probe.py`. Ключевое: ARP соседа не должен разрешаться; счётчик
`drop everything else` должен остаться нулевым (значит, первые два
правила покрывают всё).

## Чем подтверждено

Два устройства в гостевой сети, на одном SSID и на разных: ARP не
разрешается, ping 0 из 6, TCP закрыт; контрольное снятие horizon —
ARP разрешился, ping 4 из 4. Интернет и DHCP при этом работали.
