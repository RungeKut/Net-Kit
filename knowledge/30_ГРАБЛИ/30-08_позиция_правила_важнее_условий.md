# Позиция правила важнее его условий

## Что происходит

```
/ipv6 firewall filter add chain=forward in-interface=guest action=drop
```

Правило добавляется **в конец цепочки**. Выше него в стандартном наборе
стоит `defconf: accept ICMPv6`, которое пропускает трафик раньше. Правило
формально есть, фактически не действует.

## Как правильно

Указывать позицию явно:

```
/ip firewall filter add chain=forward in-interface=guest action=drop \
  place-before=[find chain=forward and comment="defconf: drop invalid"]
```

При одинаковых комментариях в разных цепочках — уточнять цепочку, иначе
`find` вернёт не то правило:

```
[find chain=input and comment="defconf: drop invalid"]
```

Несколько правил подряд с одним и тем же `place-before` встают в порядке
добавления — это как раз нужное поведение.

**После добавления — посмотреть цепочку глазами:**

```
/ip firewall filter print where chain=forward
```

## Две позиции, которые надо выбрать осознанно

**Запреты для гостей — после `accept established,related`.** Поставишь
выше — обратный трафик из интернета к гостям не пройдёт, и связь у них
пропадёт целиком.

**Запрет доступа к роутеру — перед первым разрешающим правилом, которое
может поймать трафик гостя.** Обычно это `accept ICMP`. Но если выше
стоят разрешения VPN-портов (`udp 500`, `udp 4500`, `udp 1701`,
`tcp 443`), то перед ними — иначе порты роутера останутся открыты для
гостевой сети. На разных роутерах порядок разный, смотреть надо каждый раз.

## Как неправильно

Добавить правило, увидеть его в выводе `print` и считать работу
сделанной. Наличие правила и его действие — разные вещи.

## Чем подтверждено

Два правила IPv6 после добавления оказались на позициях 24 и 25, ниже
`accept ICMPv6` на позиции 17; после пересоздания с `place-before` встали
на 3 и 4 и заработали.
