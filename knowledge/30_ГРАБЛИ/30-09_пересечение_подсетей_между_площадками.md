# Пересечение подсетей между площадками

## Что происходит

Площадка А: локальная сеть `10.N.0.0/21` — это 2048 адресов.
Площадка Б: гостевая сеть `10.N.1.0/24` — целиком **внутри** диапазона А.

Ничего не ломается заметно, пока сети не соединят туннелем. После этого:

* на площадке Б подключённый маршрут `/24` выигрывает у статического
  `/21` через туннель — как более специфичный;
* устройство на площадке А, получившее адрес из пересечения от DHCP,
  становится недоступно с площадки Б;
* любая проверка такого адреса с машины, стоящей в сети А, уходит
  **в свою же локалку** вместо туннеля.

Последнее особенно коварно: команда выполняется, ответа нет, и вывод
делается неверный — «изоляция работает».

## Как обнаружить

```powershell
Find-NetRoute -RemoteIPAddress <адрес из пересечения> | Select -First 1 IPAddress,InterfaceAlias
```

Покажет интерфейс, через который реально уйдёт пакет. Не тот — значит
измерение не состоялось.

Со стороны роутера: пустой conntrack при отправленных пакетах
([10-04](../10_API/10-04_conntrack_как_доказательство.md)).

## Как правильно

Перенумеровать одну из сетей в свободный диапазон. Проверить **все**
ссылки на старую сеть — их больше, чем видно в `print`:

```
/ip pool
/ip address
/ip dhcp-server network
/ip dhcp-server lease          статические аренды
/ip firewall filter            правила с src-address/dst-address
/ip firewall nat
/routing rule                  ← легко пропустить
/interface wireguard peers     allowed-address
```

Надёжный способ найти всё — поиск по выгрузке:

```sh
grep -n "<старая сеть>" osmotr.rsc
```

## Как неправильно

Проверить доступность адреса из пересекающегося диапазона и сделать по
результату вывод о фаерволе. Пакет туда вообще не ходил.

## Чем подтверждено

`Find-NetRoute` для адреса удалённой гостевой сети вернул интерфейс
локальной сети; после отключения этого интерфейса тот же адрес
маршрутизировался через провод и conntrack на дальнем роутере появился.
