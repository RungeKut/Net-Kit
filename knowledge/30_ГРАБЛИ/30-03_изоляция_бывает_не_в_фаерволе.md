# Изоляция бывает не в фаерволе

## Что происходит

В цепочке `forward` нет ни одного правила для гостевого моста. Вывод
«изоляции нет» напрашивается сам — и он неверен.

## Механизм 1: /routing rule

```
/routing rule
add action=unreachable dst-address=192.0.2.0/24 src-address=198.51.100.0/24
```

Это политика маршрутизации, **другая подсистема**. В `/ip firewall ...`
её не видно никогда.

Симптом, который она создаёт и который невозможно объяснить фаерволом:
роутер **принимает** ICMP (счётчик `accept ICMP` растёт ровно на число
отправленных пакетов), но **не отвечает**. Причина: его собственный ответ
уходит с адреса, попадающего под правило.

Проверка того же роутера по другому его адресу — отвечает нормально.
Это и есть подпись такого правила.

## Механизм 2: allowed-address WireGuard

WireGuard делает криптомаршрутизацию: входящий пакет принимается, только
если **адрес источника** входит в `allowed-address` пира. Иначе он
отбрасывается **до всякого фаервола**.

```
/interface wireguard peers print
→ allowed-address = <адрес пира>/32; <сеть той стороны>/24
```

Пакет из сети, которой в списке нет, уходит в туннель со своей стороны,
но на дальней стороне исчезает бесследно: ни записи в conntrack, ни
единицы на счётчиках.

**Защита настоящая, но неявная.** Достаточно кому-то расширить
`allowed-address` ради доступа к одному устройству — и сеть откроется
целиком, без подстраховки фаерволом.

## Механизм 3: arp=reply-only на мосту

```
/interface bridge add name=guest-bridge arp=reply-only
```

Роутер отвечает ARP только для адресов, выданных по DHCP, и не учит новые.
Устройство со статическим адресом вне списка аренд связи не получит.

## Как правильно

Начинать осмотр с `/export`
([10-02](../10_API/10-02_export_вместо_print.md)). Все три механизма видны
там и не видны в `print` по фаерволу.

Различать «изоляция есть» и «трафик не проходит»:
conntrack покажет, дошёл ли пакет
([10-04](../10_API/10-04_conntrack_как_доказательство.md)).

## Важная оговорка про границы такой защиты

`/routing rule` из примера режет **только обратный путь** и только для
одного источника. Пакеты из изолированной сети роутер по-прежнему
**пересылает**: conntrack показал запись, ни один `drop` не сработал.
Для TCP этого достаточно — рукопожатие не состоится. Для односторонних
воздействий — нет.

То есть «работает на практике» здесь не равно «закрыто».

## Чем подтверждено

Счётчик `accept ICMP` = 6 пакетов при 6 отправленных и нуле ответов;
на дальнем конце туннеля — пустой conntrack и нулевые счётчики;
после снятия правила маршрутизации цель немедленно ответила.
