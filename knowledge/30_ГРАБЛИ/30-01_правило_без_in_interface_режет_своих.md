# Правило без in-interface режет своих

## Что происходит

В цепочке `input` стоит правило с честным комментарием:

```
;;; drop DNS UDP from WAN
chain=input action=drop protocol=udp dst-port=53
```

Условия по интерфейсу **нет**. Правило дропает DNS откуда угодно, включая
локальную сеть.

Симптом у клиента: **пинг по IP идёт, ни один сайт не открывается**.

## Почему это ломает всё

DHCP выдаёт клиентам единственный DNS-сервер — сам роутер. Дальше:

1. клиент шлёт запрос на роутер, порт 53;
2. правило `accept established` не подходит — соединение новое;
3. правило `drop !LAN` пропускает: клиент из LAN;
4. это правило дропает.

## Второй, неочевидный вывод

Правило не только вредит — оно **бесполезно** по своему назначению.
Выше него стоит `drop in-interface-list=!LAN`, которое уже отбросило всё,
что пришло не из LAN. До правила с портом 53 доходит **только локальный
трафик**. Защиты от внешних запросов оно не даёт ни на пакет.

Это общий приём рассуждения: посмотреть, **что вообще может дойти** до
правила, с учётом всего, что стоит выше.

## Как правильно

```
/ip firewall filter set [find comment="drop DNS UDP from WAN"] in-interface-list=WAN
/ip firewall filter set [find comment="drop DNS TCP from WAN"] in-interface-list=WAN
```

Если выше уже есть `drop !LAN` — правило можно просто удалить.

## Как неправильно

Поверить комментарию и искать причину в другом месте. Комментарий
отражает намерение автора, а не поведение правила.

Второй способ ошибиться: проверить DNS со своей машины, получить ответ и
отбросить гипотезу — см. [30-02](30-02_свой_запрос_идёт_другим_путём.md).

## Чем подтверждено

Счётчик правила: 1722 пакета UDP и 115 TCP за 32 минуты аптайма при одном
активном клиенте. Счётчики **замерли** ровно в момент отключения клиента.
После правки: 0 дропов, 65 пакетов на разрешающем правиле, DNS резолвит.
