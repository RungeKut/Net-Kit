# Сети MikroTik: диагностика и настройка скриптами

Набор — git-репозиторий, общий для нескольких машин. Корень находится так:
переменная `NETKIT_HOME`, иначе `~/.claude/skills/net` — junction,
ведущий в `<корень>/skill`.

## ГЛАВНОЕ: сеть — общий ресурс

Ошибка в микроконтроллере стоит перепрошивки. Ошибка в фаерволе оставляет
без связи людей, которые об этом не просили, и может отрезать тебя самого
от роутера на другой площадке.

**Перед любым изменением правил:**

1. **Второй независимый путь до роутера** — уже проверенный, не
   предполагаемый (`knowledge/20_ПРИЁМЫ/20-01`).
2. **`/export`, забранный к себе** — до первой правки.
3. **Понять, свой это роутер или общий.** Признаки общего: чужие
   VPN-аккаунты, пробросы портов на чужие хосты, туннели до других
   площадок, устройства с чужими именами, ограничения по времени.
   На общем роутере любое изменение — **только с явного согласия
   человека**, лучше отдельным согласием на каждый шаг
   (`knowledge/30_ГРАБЛИ/30-10`).

**Без спроса можно:** любое чтение — `print`, `/export`, `/log print`,
`/ping`, conntrack; `reset-counters-all` (обнуление счётчиков ничего
не ломает и нужно для измерений).

**Только с согласия:** любое `add`, `set`, `remove`, `disable`, `enable`
в `/ip firewall`, `/ipv6 firewall`, `/routing`, `/ip address`,
`/interface`; смена адресации; создание и удаление точек доступа; всё,
что перезагружает роутер или рвёт туннель.

**Никогда:** не оставлять роутер в промежуточном состоянии между двумя
командами, если их можно выполнить одной. Отказ или обрыв может прийти
между ними.

## ОБЯЗАТЕЛЬНО: синхронизация репозитория

**В начале работы — подтянуть изменения:**

```bash
cd "$NETKIT_HOME" && git pull --rebase
```

**В набор не попадает ничего о площадке.** Репозиторий публичный, а схема
сети — готовая карта для того, кто будет её ломать. Ни в файлах, ни в
тексте коммита: адресов, публичных IP, SSID и паролей к ним, логинов,
ключей WireGuard, MAC-адресов, имён людей и устройств, пробросов портов,
состава VPN. Примеры — на `192.0.2.0/24`, `SSID-GUEST`, «роутер А».
Модель роутера и версия RouterOS — можно, они нужны в `applies_to`.

Реальные карты сетей живут в **`local/`**, он под `.gitignore`
(`knowledge/40_СРЕДА/40-03`).

**После каждого изменения набора — отправить.** Сразу, не в конце сессии:

```bash
cd "$NETKIT_HOME"
git diff                      # 1. прочитать глазами
python tools/check_docs.py    # 2. стоп-слова, адреса, MAC, ключи
git add -A && git commit -m "кратко что и почему"
git push
```

**Автор коммитов — публичный, задан для клона** (`git config user.name`
и `user.email` без `--global`). Не задан — не коммитить, а спросить
человека.

## Первое действие: осмотр начинается с /export

**Не с серии `print`.** Серия `print` показывает только то, что ты решил
спросить, и раздел, о существовании которого не думаешь, остаётся
невидимым. На реальном роутере вся изоляция гостевой сети держалась на
`/routing rule` — в `/ip firewall ...` этого не видно никогда
(`knowledge/10_API/10-02`).

```python
import os, sys
sys.path.insert(0, os.environ["NETKIT_HOME"])
import netkit as nk

r = nk.Router("192.0.2.1", user="admin")   # пароль: pw_file= или NETKIT_PW
print(r.cmd("/system resource print"))     # модель и версия — для applies_to
path = r.export("osmotr")                  # выгрузка к себе + удаление с роутера
```

Прочитать выгрузку целиком. Там видно `/routing rule`, `arp=reply-only`,
шейперы, списки доступа Wi-Fi — всё, о чём не спросишь по разделам.

## Порядок поиска неисправности

**Шаг 0 — разделить задачу надвое:** у самого роутера связь есть?

```
/ping 8.8.8.8 count=4
:put [:resolve example.com]
```

Роутер не пингует — проблема в аплинке, фаервол не трогать. Пингует,
а клиенты нет — проблема между клиентом и роутером.

**Шаг 1 — «нет интернета» не диагноз.** Разложить на три:
получил ли адрес (DHCP) · `ping 8.8.8.8` (маршрут, NAT, forward) ·
`nslookup` (DNS). **Пинг по IP идёт, сайты не открываются — почти всегда
DNS** (`knowledge/30_ГРАБЛИ/30-01`).

**Шаг 2 — читать фаервол по цепочкам, а не общим списком:**

```
/ip firewall filter print where chain=input
/ip firewall filter print where chain=forward
```

Первое совпадение выигрывает. **Несовпавший пакет разрешается** — в
RouterOS нет настраиваемой политики цепочки. Поэтому отсутствие `drop`
в конце — норма, а чужое `drop all else` меняет смысл всей цепочки.

**Шаг 3 — измерить счётчиками.** Обнулить, воспроизвести, посмотреть,
где выросло (`knowledge/10_API/10-03`).

**Шаг 4 — рассуждение о позиции.** Понять, что вообще **может дойти**
до подозрительного правила с учётом всего, что выше. Читать не
комментарий, а условия и позицию: комментарий отражает намерение автора,
а не поведение.

## Шесть правил, нарушение которых стоит часа

1. **Своя проверка идёт другим путём.** Запрос через туннель попадает под
   `accept in-interface=<туннель>` раньше ломающих правил и обходит ровно
   то, что ищешь. Проверить, откуда пришёл: `/log print where
   message~"logged in"`. Опираться на счётчики, а не на ощущения
   (`30_ГРАБЛИ/30-02`).
2. **Изоляция бывает не в фаерволе.** `/routing rule`, `allowed-address`
   WireGuard, `arp=reply-only`, `/ip firewall raw`, списки доступа Wi-Fi.
   Подпись `/routing rule`: роутер **принимает** пакет (счётчик растёт),
   но не отвечает (`30_ГРАБЛИ/30-03`).
3. **«Все drop по нулям» значит «разрешено», а не «трафика не было».**
   Различить можно только по conntrack: запись есть — дошло; записи
   нет — не дошло (`10_API/10-03`, `10_API/10-04`).
4. **Позиция правила важнее его условий.** Без `place-before` правило
   встаёт в конец и не работает. Запреты для гостей — **после**
   `accept established,related`, иначе у них пропадёт интернет
   (`30_ГРАБЛИ/30-08`).
5. **Отрицательный результат без контрольного опыта не доказывает
   ничего.** Нужна пара: с защитой не проходит, без защиты проходит
   сразу. Или та же цель из доверенной сети (`20_ПРИЁМЫ/20-04`).
6. **Никогда не выдавать непроверенное за проверенное** — ни в отчёте,
   ни в базе. В этой работе вывод «изоляции нет» был сделан по чтению
   фаервола и оказался неверным: изоляция была, в `/routing rule`.
   Помогла бы одна команда `/export`, сделанная первой.

## Гостевая сеть: четыре уровня изоляции

Фаервол закрывает только два из них (`knowledge/20_ПРИЁМЫ/20-05`).

| Уровень | Механизм | Что закрывает |
|---|---|---|
| 1 | `default-forwarding=no` на точке | гость ↔ гость на одном SSID |
| 2 | `horizon=N` одинаковый на портах моста | гость ↔ гость на разных SSID |
| 3 | forward на список `INTERNAL` | гость → внутренние сети |
| 4 | input на интерфейс гостя | гость → сервисы роутера |

Уровни 1 и 2 фаерволом **не заменяются**: трафик между клиентами моста
коммутируется до IP и в цепочки не попадает. DHCP гостям разрешить явно,
DNS выдавать внешний — тогда роутер им не нужен и закрывается целиком.

## Проверять — из той же сети, что у пострадавшего

Иначе проверка ничего не доказывает. На машине с двумя интерфейсами
трафик уходит туда, где метрика меньше; прав администратора для смены
метрик может не быть.

Windows использует strong host model: **привязка к адресу источника сама
выбирает интерфейс**, без прав администратора (`20_ПРИЁМЫ/20-03`).

```python
from netkit import probe
probe.ping("192.0.2.10", "8.8.8.8")            # ping -S
probe.http("192.0.2.10", "http://example.com") # curl --noproxy '*' --interface
probe.tcp ("192.0.2.10", "192.0.2.1", 22)      # TcpClient с локальным endpoint
probe.dns ("192.0.2.10", "8.8.8.8")            # UdpClient с локальным endpoint
```

`--noproxy '*'` обязателен: иначе curl уйдёт в `http_proxy` и обойдёт
привязку, вернув ложный успех (`30_ГРАБЛИ/30-06`).

**Результат привязки подтверждать со стороны роутера** — счётчиками или
conntrack. Не подтвердил — не измерил: подключённая сеть, покрывающая
адрес назначения, перехватит трафик независимо от намерений
(`30_ГРАБЛИ/30-09`).

Переключение Wi-Fi между сетями — `netkit.wifi`, без прав администратора.
Первая попытка подключения часто падает «сеть недоступна» из-за
устаревшего кэша сканирования; `wifi.connect()` повторяет сам
(`30_ГРАБЛИ/30-05`).

## Что делать, если доступ к роутеру пропал посреди работы

Так бывает на общем роутере: среда может отказать в правке, и чтение
тоже перестаёт быть доступным.

1. Не пытаться обойти отказ другим путём.
2. Убедиться, что роутер остался в **самосогласованном** состоянии.
   Половина перенумерации хуже, чем её отсутствие.
3. Записать в `local/`, что сделано и что осталось.
4. Передать человеку **готовые команды** для незакрытой части — с
   пояснением, почему именно такой порядок.
5. Честно сказать, что осталось непроверенным.
